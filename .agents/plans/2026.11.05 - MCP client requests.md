# MCP workspace cwd

Automatically set MCP process cwd to the workspace so relative paths and child CLIs work when the server is launched elsewhere. No new settings or consumer APIs. Implemented and verified for the supported initialization-based protocol versions; newer-protocol work is tracked separately in [MCP follow-ups](2026.11.05%20-%20MCP%20follow-ups.md).

Scope: one private roots lookup and one cwd selection per stdio session. Defer public request/session APIs and new lifecycle hooks; omit roots caching and refresh machinery. CLI/HTTP behavior stays unchanged.

## 1. ✅ Route the private roots response independently

The current read loop awaits each handler. Waiting for roots on that same path would prevent reading the client's answer.

- Read and correlate the roots response independently of queued requests and application hooks; never dispatch responses as requests
- Keep application execution serialized and MCP wire writes separate from tool output capture
- Keep the roots request internal, with a finite response timeout and cleanup on response, error, write failure, or disconnect; ignore late or unmatched responses without replying
- The timeout bounds waiting for the MCP client's roots/list response, not directory validation. Add no separate filesystem timeout machinery

## 2. ✅ Set workspace cwd once before tools run

Existing MCP configuration enables workspace cwd automatically. No opt-in or opt-out setting.

- Read roots capability from initialize; after notifications/initialized, request roots/list only from clients advertising support. Initialize declares support but does not supply workspace paths
- Settle the initial lookup and cwd selection before tool dispatch and invocation hooks, while input and response routing continue
- With exactly one root, decode its local file URI using fileURLToPath and attempt process.chdir. No separate existence probe is needed; chdir validates the directory and permissions
- Unsupported roots, zero or multiple roots, invalid or unusable paths, request errors, and timeouts preserve launch cwd and allow serving to continue; report selection or fallback through existing server logging
- Select cwd once. Later roots-change notifications do not trigger another lookup or directory switch
- Apps may override cwd through existing hooks.beforeInvoke or pass cwd to a child process
- Code running before MCP initialization still uses launch cwd; switching does not relocate already-open files or rerun earlier configuration
- Do not change gdocsmith as part of this upstream work

### Existing configuration

Once the client supplies one usable workspace root, handlers and child processes use that directory.

```typescript
const app = argsbarg({
	commands: [/* existing commands */],
	description: "Document tools.",
	key: "gdocsmith",
	mcpServer: { enabled: true },
	version: "1.0.0",
});
```

### Child CLIs inherit workspace cwd

Inside a handler, no cwd argument is needed. Pipe child output to keep it off the MCP wire.

```typescript
import { spawn } from "node:child_process";

const child = spawn("git", ["status", "--short"], {
	stdio: ["ignore", "pipe", "pipe"],
});
```

## 3. ✅ Verify and document workspace behavior

Prove a server launched outside the workspace runs tools and child CLIs inside it without consumer changes.

- Queue tools before the roots reply; verify the reply is read, cwd is selected before invocation hooks and handlers, tools stay serialized, and wire output stays clean
- Verify a child inherits workspace cwd without a cwd override; include a file URI containing encoded spaces
- Cover unsupported, empty, multiple, invalid, inaccessible, failed, and timed-out roots; fallback must preserve launch cwd. Disconnect must settle the pending wait
- Verify cwd is not changed again and an existing invocation-hook override persists
- Confirm existing supported protocol versions and clients without roots still work
- Document automatic MCP cwd behavior, the bounded client-response wait, fallback rules, and pre-initialization limits; update the implementation changelog when behavior lands
- Run focused MCP tests and typechecks, then applicable repository/template gates; preserve all template capabilities and leave Homebrew untouched unless separately authorized
- Do not bump versions, release, or publish
